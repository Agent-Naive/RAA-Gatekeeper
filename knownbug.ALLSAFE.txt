# KNOWN BUG: Certify Always Reports "Success" (ALL SAFE) Even With Violations

**Bug ID / Short Name:** ALLSAFE (Certify ignores violations in overall status)
**Severity:** High / Critical
**Status:** Open
**Discovered:** 2026-05-30 (during review of a real Certify run on the testbed folder)
**Last Updated:** 2026-05-30

---

## Summary

When running the **Certify** feature (`generate_manifest`) on a folder, the operation always returns a success message ("Success. Report stored in RAA_Vault") and is presented to the user in a success-style toast — **even when the AI has flagged multiple files as "RAA VIOLATION DETECTED"**.

The individual file lines in the ledger correctly show violations, but:
- There is no overall folder-level verdict.
- The UI treats the entire certification run as successful.
- A folder containing clear violations can still appear "certified".

This breaks the core semantic meaning of "Certify" and makes the feature misleading.

---

## Reproduction Steps

1. Run the **Certify** button (🔏 Certify tab).
2. Select a folder containing a mix of files (the original reproduction used the project's own `testbed/` folder).
3. The Certify process completes.
4. A toast appears with the text: **"Success. Report stored in RAA_Vault"**.
5. Open the newly created `.raa` ledger (Type: certify).
6. Observe that several files show `AI: RAA VIOLATION DETECTED`, yet the overall operation was presented as a clean success.

**Example ledger excerpt (real output from 2026-05-30):**

## Current Broken Behavior

- `generate_manifest` always returns `Ok("Success. Report stored in RAA_Vault".into())`.
- No aggregation of per-bucket or per-file violation status.
- The LLM call result (`report.is_error` / `report.verdict`) is used only to stamp individual lines — never to influence the overall outcome.
- Frontend (`handleCertifyFolder` in `+page.svelte`) treats any returned string as success and displays it in `.mission-success-toast`.
- A "Certify" run on a dirty folder is indistinguishable from one on a clean folder from the user's perspective.

---

## Expected Correct Behavior

- If **any** file in the folder is flagged as a violation by the oracle, the overall Certify operation must be considered a failure / "uncertified".
- The command should return a rich result (ideally `RAAReport`) containing an overall verdict (`"UNCERTIFIED"`, `"VIOLATION FOUND"`, or similar) and `is_error: true`.
- The ledger should reflect an overall status at the top level (e.g., add a clear "Overall Verdict:" line).
- The UI should present failure differently (different toast styling, message, color, or dedicated error state).
- "Certify" should only produce a trustworthy "certified" artifact when zero violations are present.

## Root Cause Analysis

### Primary Location
- `src-tauri/src/lib.rs` — function `generate_manifest` (starting ~line 408)

### Key Problems in Current Code

1. **Return type is wrong**
   ```rust
   pub async fn generate_manifest(...) -> Result<String, String>
   ```
   Compare to `scan_compressed_archive`, `scan_file_integrity`, `audit_command` etc., which all return `Result<RAAReport, String>`.

2. **No violation aggregation**
   - Inside the bucket loop, each `report` has `is_error` and `verdict`, but these are only used for the per-file ledger lines.
   - There is no `let mut any_violations = false;` style flag that gets set when `report.is_error` is true.

3. **Hardcoded success string**
   ```rust
   log_to_raa(...);
   Ok("Success. Report stored in RAA_Vault".into())
   ```

4. **Unsafe LLM fallback**
   ```rust
   .unwrap_or(RAAReport { verdict: "SAFE".into(), ... is_error: false })
   ```
   This silently treats LLM failures as clean.

5. **Frontend assumes success**
   - `src/routes/+page.svelte` lines ~497-527 (`handleCertifyFolder`)
   - Result is stored in `certMsg` and displayed in a success-themed overlay (`.mission-success-toast`).

6. **Ledger writing is flat and lacks overall status**
   - Only individual `File: ... | Hash: ... | AI: ...` lines are written.
   - No top-level summary verdict for the entire certify run.

### Related Design Issues

- Heavy bucketing (10k char limit) means one LLM call can cover many files. A single "VIOLATION" verdict gets applied broadly.
- The recent Archive redesign (per-file rich `--- RAA FILE ANALYSIS ---` blocks) has not yet been applied to Certify. Certify still uses the old flat format.

## Detailed Fix Requirements

### Rust Side (`src-tauri/src/lib.rs`)

- Change `generate_manifest` signature to return `Result<RAAReport, String>` (for consistency).
- Introduce violation tracking:
  ```rust
  let mut any_violations = false;
  ...
  if report.is_error { any_violations = true; }
  ```
- Build a proper `RAAReport` at the end:
  - `verdict`: "UNCERTIFIED" / "VIOLATION FOUND" when any violations, else "CERTIFIED" / "ALL SAFE"
  - `reasoning`: The full `ledger_entries` string (or richer version once we upgrade the format)
  - `is_error`: `any_violations`
  - `target_name`: the folder path
- Improve the ledger output for certify runs (add overall status line near the top of the report).
- Consider making the LLM fallback more honest (mark as error instead of defaulting to SAFE).
- (Longer term) Decide whether to keep aggressive bucketing or move toward per-file (or very small batch) oracle calls now that we want trustworthy per-file results (see recent Archive changes).

### Frontend Side (`src/routes/+page.svelte`)

- Update `handleCertifyFolder` to handle a richer response (or keep string for now and parse status from it).
- Change how `certMsg` (or a new `certResult`) is displayed:
  - Different styling for success vs failure.
  - Possibly surface the overall verdict prominently.
- Consider showing a summary count: "X files audited, Y violations found" instead of just the raw success string.

### Ledger Format Considerations

- Current Certify output is still the old flat style.
- When we later apply the rich per-file format (like we did for Archive), we must ensure the overall violation status is still clearly visible at the top of the report.
- The DNA extraction regex must continue to work.

### Testing Requirements

- Test with a folder containing:
  - Only clean files → should certify cleanly.
  - Mix of clean + violations → must report as uncertified / failure.
  - Edge case: LLM failure on one file during bucketing.
- Verify both the `.raa` file content and the in-app feedback after running Certify.

## Related Work & Context

- Recent improvement: Archive (ZIP) audits now correctly persist full per-file AI reasoning (see `scan_compressed_archive` changes and `--- RAA FILE ANALYSIS ---` blocks).
- Certify was deliberately designed with bucketing for cost control. This bug shows the current design trades away correctness for cost.
- The phrase "Trust, then Certify." at the bottom of ROADMAP.md is currently ironic for the Certify feature.

---

## Suggested Implementation Approach (Small Slices)

1. **Minimal correctness fix** (high priority):
   - Add violation aggregation in `generate_manifest`.
   - Change return type to `RAAReport`.
   - Update frontend to show failure state when `is_error` is true.
   - Keep existing bucketing for now.

2. **Ledger output improvement**:
   - Add a clear overall verdict line when writing the certify report.

3. **Later (after Archive pattern is stable)**:
   - Upgrade Certify to use the new rich per-file analysis blocks.
   - Re-evaluate bucketing strategy now that trustworthy per-file results are a requirement.

---

## Acceptance Criteria (for the fix)

- Running Certify on a folder with one or more violations must **never** return a pure success result.
- The UI must clearly communicate that certification failed / the folder is uncertified.
- The generated `.raa` ledger must contain an unambiguous top-level indication of overall status.
- Existing DNA hash extraction must continue to function.
- No regression on clean-folder certification runs.
